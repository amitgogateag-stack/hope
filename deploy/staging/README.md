# Isolated non-trading preview release

This is a **new preview-only staging implementation**, not the existing
operations dashboard, a PAPER image, a schema upgrade or independent acceptance.
It has no connected research/portfolio data. Never substitute it for the
existing dashboards or call it a full application/database deployment.

## Explicit surface and trust boundary

The deterministic ZIP contains exactly server.py, index.html, manage.py,
deploy.sh, rollback.sh and MANIFEST.json. No HOPE application package, broker,
factory, scheduler, exporter, credentials, dependencies or migrations is shipped.
The standalone server imports only Python's standard library, binds only
127.0.0.1:8790, and serves two exact routes: `/` and `/status.json`. It has no
file-server/upload/execution endpoint. POST is denied. Runtime JSON reports
PAPER/LIVE/execution false, database NOT_CONNECTED, broker NOT_INCLUDED,
independent acceptance UNVERIFIED and operational readiness BLOCKED. These
fields describe this isolated preview, not the current host's trading state.

The kernel/interpreter/system administrator remain trusted. `-I -S -B` removes
ambient Python imports/site customization/bytecode writes. A runtime audit hook
rejects outgoing socket connections, subprocess/exec/system launches, SQLite,
dynamic library loading and file writes. This is defense in depth, not a claim
that Python audit hooks sandbox hostile arbitrary code. There are no plugins,
dynamic imports or caller-provided source inputs in the preview artifact.

## Reproducible build (local, no remote deployment)

From the immutable source containing these files:

```text
python -m hope.api.staging_release --repo VERIFIED_CHECKOUT --commit EXACT_40_HEX_COMMIT --output HOPE_NOV15_STAGING_RELEASE.zip
```

The builder reads only committed blobs, not dirty checkout bytes, uses a scrubbed
Git environment/no replacement objects/hooks, fixed ZIP timestamps/order/modes,
stored compression, exclusive output creation and a SHA256 file manifest.
Rebuilding the same commit produces identical bytes. Hashes are integrity
checks, not cryptographic independent signing authority. Review/pin the external
archive checksum before running anything from it.

## Mandatory predeployment gates — STOP while any is unavailable

User-reported EC2 facts do not establish Codex connectivity or restore success.
Readable backup TOC and a matching backup SHA256 are not a restore rehearsal.
Require a complete restore into a separately authorized disposable destination,
integrity/count/identity checks and timing; never restore into database `hope`.
No restore provisioning, production credentials/grants or backup mutation is
performed by this tool. Capacity, exact baseline of BOTH legacy/current units,
ports8787/8788, current release and staging isolation must be recorded and
independently checked. Inspect existing trading unit/timer absence without
stopping, disabling or modifying any existing unit.

The installer requires a root-owned, non-group/world-writable operator declaration
and seven real root-owned evidence documents under protected parents. This is an
accountable HUMAN staging precondition, **not independent PAPER authority**.
It validates ownership, file hashes, schema, exact commit and a thirty-minute
declaration window; it cannot decide whether a human restore report is truthful.
Review evidence semantics before issuing the declaration. No sample populated
PASS file is supplied; do not invent proof to satisfy the parser.

Declaration schema (field descriptions, not a passing configuration):

- schema: `hope.staging-operator-gates.v1`
- commit: exact reviewed commit, not HEAD/branch/ref
- operator: accountable operator name
- recorded_at: actual timezone-aware ISO timestamp after evidence review
- evidence: EXACT keys `restore_rehearsal`, `backup_integrity`, `capacity`,
  `service_baseline`, `isolated_paths`, `nontrading_review`, `rollback_rehearsal`.
  Each value has EXACT keys `path` (absolute evidence file) and `sha256`
  (actual file digest). Combined real reports may cover multiple requirements.

These gates are deliberately not generated by build/install/test commands.

The executing `manage.py` must itself be root-owned under protected parents and
byte-for-byte identical to the `manage.py` member in the externally checksum-pinned
archive. This consistency check detects the wrong or accidentally altered operator
tool; it does not replace external archive verification, review or trusted root.

Do NOT run installation until the exact source/PR CI, artifact review, all seven
evidence records and all ten user safety conditions pass. The top-level delivered

fetch an unverified mutable branch. Use the existing authorized transfer method

After reviewed transfer and safe local ZIP verification/extraction into a NEW
operator directory, the exact operator invocation is:

```sh
sudo /usr/bin/python3 -I -S -B /ABSOLUTE_REVIEWED_TOOLS/manage.py install \
  --archive /ABSOLUTE_REVIEWED_ARCHIVE/HOPE_NOV15_STAGING_RELEASE.zip \
  --archive-sha256 EXACT_EXTERNAL_SHA256 \
  --commit EXACT_REVIEWED_40_HEX_COMMIT \
  --gates /ABSOLUTE_PROTECTED_EVIDENCE/operator-gates.json
```

Equivalent reviewed shell wrapper: `sh deploy.sh` with the same arguments.
Never run a full operations activation/install script for preview staging.

The installer creates ONLY `/opt/hope-staging/releases/COMMIT` and a NEW transient
`hope-staging-preview.service`. The latter is defined by this implementation;
it is not asserted to exist on EC2. No persistent unit, timer, enable-on-boot,
current pointer, production config, database, existing service or dependency
installation is used. DynamicUser, read-only filesystem/home/device/kernel
restrictions, empty capability set, loopback-only network policy and bounded
resources are required properties. Interpreter/control/DB/factory environment
variables are removed; the actual launch is fixed to the artifact server.
Unsupported systemd properties must cause investigation, not weakening.
START_REQUESTED is not health/acceptance. A crash/failed install retains files
and requires manual investigation; do not delete evidence or rerun over a release.
Before returning START_REQUESTED, the installer reads back the transient unit's
commit-bound identity and effective DynamicUser, privilege, filesystem, home,
temporary-directory, device and loopback-only network restrictions. A weaker or
mismatched unit is stopped and the launch is refused. This read-back does not
prove kernel enforcement or constitute host/PAPER acceptance.

## Staging-only rollback

```sh
sudo /usr/bin/python3 -I -S -B /ABSOLUTE_REVIEWED_TOOLS/manage.py rollback --commit EXACT_REVIEWED_40_HEX_COMMIT
```

Equivalent wrapper: `sh rollback.sh --commit ...`. Rollback requires the exact
transient unit description, working directory, effective sandbox properties and
safe release parents.
It stops ONLY `hope-staging-preview.service`, confirms inactive/absent state,
and retains the release and evidence. No recursive deletion, prior-release
switch, production restart or DB restore occurs. No active preview means there
is nothing to roll back; unexpected identity is a denial requiring inspection.

Actual systemd startup, stop and repeated restart/rollback on EC2 remain NOT
EXECUTED until separately recorded. Disposable Linux HTTP tests and modeled
systemd command tests are not a remote host rehearsal.
