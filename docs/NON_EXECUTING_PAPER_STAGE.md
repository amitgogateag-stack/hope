# Non-executing PAPER stage and independent receipt verification

## Boundary and remaining handoff

The running deployment collector requires CURRENT PAPER health, including a
successful cycle and compatible schema. The pinned worker guard requires that
deployment proof before factory import/first cycle. Those requirements cannot
bootstrap each other. Running readiness must not be made green by ignoring a
missing heartbeat or fabricating a successful cycle.

This batch adds a distinct **non-executing stage**. The authenticated bootstrap
can hold a real process with its final trusted release Python, exact argv and
source/runtime bindings while an independent operator observes/signs its actual
identity. A separate collector authenticates that process and the independently
provided receipt, returning STAGED, never VERIFIED/CURRENT/PAPER_READY.

This is the process/receipt verification prerequisite, not a completed activation
handoff. There is no command, token or watcher which converts this process into
an executing worker. The existing controller running-proof validator, worker
admission and operational preflight reject the staged schema. The circular first
cycle gate remains a blocker for actual execution until an explicitly reviewed,
independently authorized activation transition is engineered. No execution gate
or financial safety check is weakened by this stage path.

## Reviewed bootstrap and lifecycle

The established OS trust-anchor bootstrap independently authenticates release
source, interpreter, runtime manifest and package/build provenance before the
release Python is executed. `--stage-only` requires release-specific runtime
selection, cannot combine with database preflight and does not dispatch the
PAPER worker. Its second-stage environment forwards only the fixed OS environment,
deployed SHA and LIVE=false; database URLs, loader/import variables and systemd
notification/watchdog settings are omitted.

Canonical second-stage argv is bound by the independently signed deployment
receipt. The executable is the approved `/opt/hope-operations/release-venvs/SHA/bin/python`,
followed by `-I -B -X pycache_prefix=/nonexistent/hope-runtime-bootstrap`, the reviewed
`releases/SHA/deploy/operations/paper_release.py`, and exactly:

```text
--approved-runtime-manifest <SHA256> --runtime-mode release --stage-only --factory <approved.module:function> --stage-request <64-hex-nonce> --stage-timeout <1..300>
```

The factory is an identity string only: it is never imported or called. No DB
engine is created, credentials loaded, financial state changed, READY notification
sent, activation authority consumed or service executed. The loop publishes a
WAITING heartbeat once per second, stops at its bounded monotonic deadline or
signal, then publishes STOPPED if it still owns its lease. No running PAPER health
file is changed. SIGKILL leaves a stale private observation but releases its kernel
lock; that observation cannot satisfy the staged collector.

`root/staging` must already exist with separately approved ownership, canonical
path and no group/world writer. No directory provisioning, mount, account,
systemd or AWS operation is performed by this code. Its `paper-stage.json` and
existing publisher lock use established private durable publication and exclusive
ownership. Rejected, replaced or released owners cannot overwrite a successor.
Running this on a real host is a process/host operation requiring separate
explicit authorization; only disposable local/CI processes were used here.

## Independent stage inspection

`inspect_staged_deployment` reuses the SAME deployment implementation for source,
immutable receipt/signature, role separation/revocation, production image/SBOM,
package/build provenance, real provider/data/calendar acceptance, rollback,
read-only PostgreSQL host compatibility, actual container and kernel identity,
and exact source/runtime namespace bindings. None of those gates is optional.
No approval, key, dataset or receipt is generated by this API.

The stage-specific observation replaces the *running* systemd/heartbeat readiness
question with a non-execution identity question. It does not attest systemd unit
readiness. It independently binds the stage file/directory/lock in the process's
namespace to the same host inodes and kernel UID, checks the current exclusive
publisher lease, process incarnation, canonical bootstrap argv and signed process
digest, exact approved factory and request nonce, WAITING and execution=false.
Future, stale (>5 seconds), malformed, STOPPED or contradictory observations fail.

The collector closes on that same immutable ownership/nonce/namespace binding
after rechecking all independent approvals and source/runtime evidence under the
shared activation fence. Its expiry is bounded by the last heartbeat's five-second
window and every signed approval's expiry. A restarted process needs a new
independent receipt because its kernel identity and publisher nonce change.
The established activation journal validator is also used before and after
inspection: interrupted, corrupt or concurrently changed journals block staging
proof rather than being repaired, ignored or converted into running readiness.
Full activation's durable lease must be ABSENT according to the existing recovery
inspector; stale, corrupt or unreadable leases also fail closed.

`paper_controller inspect-stage --directory <existing-controller> --root <approved-root>`
reads the journal's pinned release/receipt/factory without recovering or writing
that journal. HALTED controllers refuse inspection. The default collector has
no DB credentials/connection; callers need an explicitly supplied read-only
host probe for PostgreSQL evidence, otherwise stage inspection stays BLOCKED.
The API accepts that same established read-only host-probe mechanism; it never
silently assumes compatibility. Exit zero means STAGED evidence only, not worker
admission or authority to run PAPER.

`GET /staging.json` provides the bounded fixed-path observation. It exposes the
safe stage/deployment schema and fixed blockers, not raw factory strings, process
argv, paths, environment or private heartbeat contents. Main deployment and
controller endpoints remain unchanged and cannot consume STAGED as running proof.

## Verification and limitations

Synthetic contract tests cover missing/expired/invalid/revoked approvals,
provider/image/runtime mismatches, kernel/namespace/argv substitutions, changed
nonce/ownership, stale/future heartbeat, concurrent STOPPED transitions and strict
separation from running admission. Namespace metadata models are explicitly
synthetic. Native Linux tests separately exercise real process signals, SIGKILL,
lease exclusion, restart incarnation, deadline and zero factory/database effects.
Existing native OCI process, signature, PostgreSQL 16/17 and regression suites
remain required. These tests do not establish a production namespace binding or
real-provider/host acceptance.

No AWS connection, deployment, mount, service activation, production DB mutation,
credential modification, actual PAPER execution, strategy/risk change or merge
is performed. LIVE stays disabled; the frozen baseline is untouched. Next: review
the distinct independently authorized stage-to-first-cycle transition, then
perform host/real-data acceptance only after separate explicit authorization.
